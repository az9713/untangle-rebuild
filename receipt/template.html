7. Score, fidelity and gaps

Score: 52 correct, 2 partly correct (C50 says "floor" where C truncates; C52 says the first arrow press selects point 0, which A1 had already corrected), 0 wrong, 3 not checkable from source (C1, C3, C4 are facts about the binary file). 52 / 54 = 96.3 %. Addendum: 7 / 7.

Fidelity: L1 (rules, look, playable to a win: REA browser scenario won a game by keyboard), L2 (game-ID format; the same ID gives the same puzzle), and L3: the grader found no algorithm difference between the rebuild's generator and untangle.c/random.c/tree234.c; the phase 6 run showed the same start graph for seed 123456789012345, and the rebuild's solution solved the original.

Rebuild differences found by the grader: keyboard (Space should cycle, not pick up; Shift+Tab does not reverse on Windows), no midend key shortcuts (u, r, n, q, Ctrl+Z…), no "Keyboard shortcuts without Ctrl" preference, Restart animates in the rebuild but not in the original, no undo of New Game, grey 0.5 rounds to 128 instead of 127, text not bold, anti-aliased lines, a trailing comma in a description adds a NaN edge, and the ID box trims spaces.

No remembered factsRisk, not provableClaude Code showed this notice during the run: "The model likely saw Untangle's public source code during training … score can still include remembered knowledge." Every claim cites REA evidence, and no claim was marked prior-knowledge, but I cannot prove that memory did not steer which REA calls I made or how I read pseudocode. 10. REA limits and unknown unknowns found in this run

  1. No native UI capture on Windows (known before the run): REA 6.3.0 cannot screenshot or click a Windows window, so the original was never observed through REA.
  2. inspect_signature needs macOS. On Windows it returns capability_unavailable ("Native macOS utilities require macOS"). The Authenticode blob was found only by parsing the PE header from read_bytes by hand.
  3. Ghidra left 7 of the game's functions undefined (small leaf functions reached only through the function-pointer table). batch_decompile failed on them ("No procedure exists at the requested address"); read_bytes plus hand decoding of x86-64 was the workaround. A reader of REA output alone would miss these functions.
  4. Results are larger than the client's tool-result limit. Most decompile, string and screenshot results (55–140 K characters) were saved to files and read with node; the 10 MB MCP budget was never the limit.
  5. The exported evidence bundle carries records from earlier sessions (8 of 49 records were from the session-4 REA-on-REA run; evidence/questions.md says 7, which is a miscount) and is 72 MB for 49 records, mostly inline payloads.
  6. capture_browser_scenario has no drag action, so REA could test keyboard play to a win but not mouse dragging.
  7. Where REA-guided analysis missed facts: all 22 "missed facts" from the grader are in the midend or the Windows front end (key shortcuts, Space vs Enter, Shift+Tab, Restart behaviour, font weight, GDI pixel rules). The game file itself (untangle.c) was covered almost completely. The cause is scope: I followed the game's function table, not the shared front-end code.
  8. Prior-knowledge risk (see rule 4): for a widely published open-source program, an "REA-only" score is an upper bound on what REA alone would give a model that has never seen the source.
