10. REA limits and unknown unknowns found in this run

  1. No native UI capture on Windows (known before the run): REA 6.3.0 cannot screenshot or click a Windows window, so the original was never observed through REA.
  2. inspect_signature needs macOS. On Windows it returns capability_unavailable ("Native macOS utilities require macOS"). The Authenticode blob was found only by parsing the PE header from read_bytes by hand.
  3. Ghidra left 7 of the game's functions undefined (small leaf functions reached only through the function-pointer table). batch_decompile failed on them ("No procedure exists at the requested address"); read_bytes plus hand decoding of x86-64 was the workaround. A reader of REA output alone would miss these functions.
  4. Results are larger than the client's tool-result limit. Most decompile, string and screenshot results (55–140 K characters) were saved to files and read with node; the 10 MB MCP budget was never the limit.
  5. The exported evidence bundle carries records from earlier sessions (8 of 49 records were from the session-4 REA-on-REA run; evidence/questions.md says 7, which is a miscount) and is 72 MB for 49 records, mostly inline payloads.
  6. capture_browser_scenario has no drag action, so REA could test keyboard play to a win but not mouse dragging.
  7. Where REA-guided analysis missed facts: of the grader's 22 "missed facts", 13 cite only midend.c/windows.c (key shortcuts, Shift+Tab, Restart, New-game undo, font weight, GDI pixel rules, tile-size rule), 3 cite both those files and untangle.c, 5 cite only untangle.c (cursor-search edge cases, keyboard pick-up without snap, first flash frame, 32-bit overflow), and 1 cites misc.c. So the largest share is shared front-end code; the 5 untangle.c details compare with 52 correct claims. The cause is scope: I followed the game's function table, not the shared front-end code.
  8. Prior-knowledge risk (see rule 4): for a widely published open-source program, an "REA-only" score is an upper bound on what REA alone would give a model that has never seen the source.

11. How the reverse engineering was done

Added 2026-10-11, after the test, with the source key available. The key is used here only in the "source key" columns and in the name audit. Nothing in sections 1–10 depends on this section. Times are −0700 (the REA ledger in section 8 shows the same calls in UTC, 7 hours later).

Short answers.

  1. Did REA look at the binary? Yes. REA opened target/untangle.exe (167,496 bytes) itself. It did not use the source, the help or a web version. All 45 REA calls in phase 2 read this one file.
  2. Which engine? Ghidra 12.1.4, run headless by REA 6.3.0. The evidence bundle lists one engine, ghidra, plus four REA-internal providers. Analysis profile: analyzer_preset ghidra-default, import_mode ephemeral-source-immutable, process_launch official-headless-script-v1. Ghidra imported a temporary copy; the exe bytes were never written.
  3. Hopper? No. Hopper is a macOS disassembler. On Windows, REA's Hopper provider reports unsupported_host ("not supported on win32"; seen in the session-4 REA test). IDA was not installed (not_configured). Ghidra was the only engine available, and the only one used.
  4. C or C++? C. Evidence from REA: the 8 assert paths in the binary end in .c (/puzzles/untangle.c, random.c, midend.c, windows.c, misc.c, tree234.c, drawing.c, printing.c; ev_050a2cb0). The imported DLLs are the C runtime (VCRUNTIME140.dll, 9 api-ms-win-crt-* DLLs) and Win32 (USER32, KERNEL32, GDI32, COMDLG32, COMCTL32). There is no MSVCP140.dll (the C++ standard library), and the strings contain no type_info or std::. The key confirms it: 74 .c files, 0 .cpp files. Note: Ghidra always writes C-like pseudocode, whatever the source language was.
  5. Did REA recover the source code? No. Ghidra gave C-like pseudocode: functions named FUN_140001080, variables named param_1, uVar2, types such as undefined8, no comments, no macros, no struct fields. 7 of the game's 31 functions were not decompiled at all, because Ghidra had not defined them. The model (Claude Opus 5.5) read the pseudocode and the raw bytes, wrote 57 claims in English, and then wrote a new program in JavaScript. No C source was written at any step.
  6. Did REA watch the original run? No. REA 6.3.0 cannot capture a Windows window (gap G1). The 16 REA calls after phase 2 were browser captures of the rebuild in Chrome. The left half of the GIF (the original) came from PowerShell CopyFromScreen, not from REA.
  7. How much came from training memory? This cannot be measured as a percentage, because the same model did the analysis and holds the memory, and there was no control run with a model that has never seen this source. What can be measured is in 11.5: the facts are tied to REA output and are written in the shape of the compiled code; 10 names came from memory.

11.2 The phase 2 call sequence (22:36:37 – 22:47:26, 45 REA calls, about 11 minutes)

  1. Open. open_binary (22:36:37): Ghidra imports the exe and runs auto-analysis. binary_overview (22:36:38, ev_dc3bb3d4): 457 procedures, 469 strings, 9 segments (.text 90,112 bytes, .rdata, .data, .rsrc and others).
  2. Read the text in the file. list_strings (22:37:26, ev_050a2cb0) gave the version string, the menu texts, the error messages, the DLL names and the 8 assert paths. The assert paths were the first map: they name the source files linked into the exe.
  3. Find the game's function table. xrefs (22:37:44) on the string "Untangle" at 0x14001800e (ev_54a33ea7) and on "/puzzles/untangle.c" at 0x140018a14 (ev_474fa8cb). The first led to a data table at 0x140017000. read_bytes of 512 bytes there (ev_f3e4cc63) gave the raw table; a node script split it into 8-byte pointers: 32 code-pointer slots that hold 31 different function addresses, from 0x140001080 to 0x140003f10, plus numbers such as 64 (tile size) and the preset list.
  4. Decompile the table's functions. batch_decompile (22:38:09, ev_f7ad8758; an 87,013-byte record) returned pseudocode for 24 of the 31. For the other 7, Ghidra answered "No procedure exists at the requested address". inspect_native_instruction and read_bytes (22:39–22:42) gave their bytes, and the model decoded the x86-64 by hand (example 3 below).
  5. Follow the calls out of the game code. procedure_callees, procedure_callers and more batch_decompile / procedure_pseudo_code calls (22:40–22:45) reached the random-number code (0x140015140, 0x140015270, 0x140015630; ev_da809602, ev_2287f35a, ev_0c928f90), the square root and crossing test (ev_571db767), the game-ID parser (0x140012de0, ev_cb816f3e, found through search_procedures for strchr, ev_08f9d4a5), the menu builder (0x14000aa38, ev_979e13f3, found from xrefs on "&Restart", ev_5fd758c5) and the seed maker (ev_951dd08d). procedure_assembly on the redraw function 0x1400039b0 (ev_ca98285d) checked the drawing order instruction by instruction.
  6. Save and close the record. export_evidence_bundle (22:46:11) wrote all records to a 72 MB JSON file. inspect_signature (22:47:22) failed: it needs macOS. A last read_bytes (22:47:26) read the PE header, which the model parsed by hand for C3 and C4.

Then the model wrote the findings (phase 3, frozen 22:49:55) and the rebuild (phase 4). The source was downloaded at 23:01:43, after both.

The compiler joined bits += 3 and 1L << bits into 8 << b; the rebuild copies the compiled form, not the source form.

Model wrote (rebuild/index.html:101-107)

function randomUpto(rs, limit) {
  // C13 ev_0c928f90 (0x140015630)
  let b = 0;
  while (Math.floor(limit / Math.pow(2, b))
         !== 0) b++;
  if (b > 28) throw new Error("bits < 32");
  const divisor = Math.floor(
    ((8 * Math.pow(2, b)) >>> 0) / limit);
  let v;
  do { v = randomBits(rs, b + 3); }
  while (divisor * limit <= v);
  return Math.floor(v / divisor);
}

Source key (random.c:266-286)

unsigned long random_upto(random_state *state,
                          unsigned long limit)
{
    int bits = 0;
    unsigned long max, divisor, data;

    while ((limit >> bits) != 0)
        bits++;

    bits += 3;
    assert(bits < 32);

    max = 1L << bits;
    divisor = max / limit;
    max = limit * divisor;

    do {
        data = random_bits(state, bits);
    } while (data >= max);

    return data / divisor;
}

11.4 How the rebuild was made from the claims

The model wrote rebuild/index.html as one HTML file with plain JavaScript and a canvas. Each part copies the behaviour of one decompiled function: SHA-1 and the random-number code (C10–C15), the generator (C24–C29), the start circle (C30), the crossing test with 64-bit products through BigInt (C32), solve (C56), drawing (C37–C48) and input (C49–C55). Where REA gave no fact, the code has a placeholder marked gap (for example the background colour, G2, and the font, G6). Because the random-number code, the generator and the ID format were copied exactly, the same game ID gives the same puzzle as the original (fidelity L3, section 7).

Signs that memory was used

  1. The 10 names in the table above. REA showed these functions only as FUN_… addresses. The model wrote the exact names used in the Puzzle Collection source. A model with no memory of this code base would have had to invent names, and they would not match. These names should have been marked prior-knowledge (rule 4). They were not. This is a rule 4 break found after the test.
  2. The role list in C7 gives English roles for 29 of the 31 table addresses ("decode params", "interpret move", "execute move", "flash length" …). The grader wrote: "The role order agrees with the struct order." The roles were inferred from what each function body does, but knowledge of the framework's struct game very likely made this faster and surer. C7 does not name 3 slots (free_params, dup_params, free_ui; 2 addresses, 0x1400011b0 and 0x1400011c0). A full recall of the table would probably have named them too.
  3. The meaning of tree234 as a sorted 2-3-4 tree (gap G8) came from its name in an assert path plus general knowledge, not from decompiling it.

General knowledge, not knowledge of this program

  1. SHA-1 was named from its published constants (67452301 efcdab89 …), which REA returned in the pseudocode (C11).
  2. GetSysColor(4) was named COLOR_MENU: the Windows SDK constant name for 4. The source also uses COLOR_MENU (windows.c:342).
  3. The 240-grey background placeholder (marked gap G2). The original turned out to show 240,240,240 on this laptop.

Signs that the facts came from the binary

  1. Each of the 57 claims cites one or more REA evidence IDs, and 33 lines of the rebuild cite one.
  2. Claims use the compiled form, not the source form: C20 says n ≥ 715,827,883 (0x2aaaaaab) where the source says n > INT_MAX / 3; C13 says (8 << b) / limit and random_bits(b + 3) where the source says bits += 3; max = 1L << bits; C24 says floor(sqrt(3n)) where the source says COORDLIMIT(n) squarert((n) * POINTDENSITY).
  3. The 2 partly-correct claims are errors of reading pseudocode: C50 says "floor" where C division truncates, and C52 misread an if (cursor < 0) cursor = 0 line.
  4. Memory did not fill the gaps: of the grader's 22 missed facts, 13 are in midend.c/windows.c, code that the model decompiled only in part (the game-ID parser, the seed maker and the menu builder). The claims leave those facts out; they do not recall them.

Conclusion. The facts in the findings are tied to REA output: each has an evidence ID, they use the compiled form, and 52 of 54 checkable claims match the source. The names, and probably some of the speed of the role mapping, came from memory of the public source. Memory may also have steered which addresses the model chose to read; that part cannot be measured from the record. So the score of 96.3 % is an upper bound for a model that has never seen this source. A clean measure needs a target that is not public, or a program written after the model's training cut-off.
